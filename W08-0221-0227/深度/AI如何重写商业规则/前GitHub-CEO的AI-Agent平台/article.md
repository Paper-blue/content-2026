# 所有人都在让AI写代码，但没人解决AI写的代码该怎么管

> 系列：AI如何重写商业规则
> 发布日期：2026-02-21

---

2026 年 2 月 10 日，旧金山，一个 15 人的远程团队正式对外亮相。

创始人叫 Thomas Dohmke，在此之前，他在 GitHub 当了四年 CEO。离职时间是 **2025 年 8 月**。

融资额是 **6000 万美元**。

种子轮，6000 万美元。

这是什么概念？PitchBook 的数据显示，这是开发者工具领域**有史以来最大的种子轮**。没有先例，没有接近的第二名。

新公司叫 Entire。产品叫 Checkpoints。

他们要解决的核心问题，用一句话说清楚就是：**当 AI 开始大规模替人类写代码，谁来管理 AI 写的代码？**

---

## 一、飞轮

要理解 Entire 这个公司，得先理解它的历史前身 GitHub 做对了什么。

2008 年，GitHub 上线。它解决的是一个很具体的协作问题：代码怎么让多个工程师同时改、同时维护、出了问题怎么回滚？

答案是 Git + 网页界面。

功能本身并不复杂。Git 是 Linus Torvalds 在 2005 年就写出来的工具，开源的，任何人都能拿来用。GitHub 做的，是给 Git 套了一层漂亮的 UI，加了 Issue 追踪、Pull Request 审核、Wiki 文档……把**命令行工具**变成了一个协作平台。

但真正让 GitHub 变成平台帝国的，不是这些功能，而是它锁住了**开发者的社交图谱**。

你在 GitHub 上有 commit 历史、star 记录、开源项目贡献、公司内部的同事关系……这些东西比代码本身更难迁移。当 GitHub 的注册用户达到 5000 万的时候，这个平台已经不只是一个工具，而是开发者的**职业身份证明**。

去面试，HR 问"你的 GitHub 主页是什么"？

这句话背后的含义，是在问你过去写了什么、参与了哪些项目、在开源社区里有没有声誉。

微软在 2018 年用 **75 亿美元**收购了 GitHub。

当时很多人不理解——GitHub 不盈利，产品也没有什么技术壁垒，为什么值 75 亿？

后来的事证明了答案：不是因为代码托管的功能，是因为那 **5000 万开发者**。

2021 年，Nat Friedman（Dohmke 的前任，GitHub 的前一任 CEO）主导推出了 GitHub Copilot。一个能在你写代码时实时补全的 AI 助手。

它的设计逻辑极其简单：你在哪里写代码，AI 就在哪里陪着你。不改变工作流，不需要学新工具，只是在你原有的编辑器里多出来一个"懂代码"的副驾驶。

这个设计决策，现在回头看，是有深意的。

AI 写代码助手的竞争对手有很多——JetBrains 的 AI Assistant、Amazon 的 CodeWhisperer……但 Copilot 的优势不是功能最强，而是**它在最多开发者已经在用的地方出现了**。GitHub 的 9000 万开发者，本来就每天要上去 push 代码、看 PR；Copilot 就在这里等着，接入成本几乎为零。

Copilot 变成了 GitHub 历史上增长最快的产品。

到 2025 年，付费用户超过 130 万，企业客户超过 5 万家，Fortune 100 里有 90% 的公司在用。Satya Nadella 在一次财报电话会议里说了一句话，很多人没太注意：**GitHub Copilot 现在的业务体量，已经超过了 2018 年微软收购整个 GitHub 时候的规模。**

75 亿美元的收购，买来了一个比自身体量还大的增量业务。

这是一个飞轮在转：代码托管积累了开发者，开发者产生了海量代码数据，数据训练了 AI，AI 让开发者更离不开 GitHub，更离不开意味着更多数据，更多数据意味着更好的 AI……

这个飞轮，是 Entire 的起点，也是 Entire 要解决的那个问题的来源。

但飞轮运转到一定速度，会产生一个副作用。一个在 2024 年才开始显现的副作用。

---

## 二、裂缝

Copilot 让 AI 写代码变成了日常。但随着 AI 能力的快速迭代，一件事正在悄悄发生：

代码生成的速度，正在超出人类理解和审核的速度。

2021 年的 Copilot，是一个补全工具。你写一半，它帮你补另一半。人还在主导，AI 在辅助。

但到了 2024、2025 年，这件事发生了质变。

Claude Code、Gemini CLI、Cursor——这些工具已经可以自主完成从理解需求、写代码、写测试、跑测试、提 PR 的**完整开发流程**。你给它一个功能描述，它能在几分钟内交付一个可运行的版本，全程不需要人类盯着。

这就是所谓的"AI Agent 时代"。

对工程团队来说，这意味着什么？

意味着**一个中等规模的工程团队，如果充分使用 AI Agent，每天可以产出的代码量，可能是过去纯人工状态的 10 倍甚至更多**。

10 倍的代码产出，但能做 Code Review 的工程师数量还是原来那些。

这里有一个被大多数人忽视的结构性矛盾。

GitHub 的整套工作流——从 Issue 到 Pull Request 到 Code Review 到部署——是为一个前提设计的：**代码是人写的，写代码的人能解释他们的每一个设计决策。**

PR 的描述写"Fix authentication bug"，Review 的人可以去找写这段代码的工程师问"为什么这里用递归不用迭代"，工程师能答上来，因为他当时是这么想的。

但 AI 写的代码不是这样。

你让 Claude 帮你写一个认证模块，它吐出 300 行代码，测试全过，功能完美。但那个做 Code Review 的同事打开文件，发现他根本不知道：这里为什么用递归不用迭代？这个设计决策是 AI 第一次给出的答案，还是经过反复调整之后的最终结果？那 300 行代码里有没有 AI 自己引入的安全漏洞？如果三个月后线上出了问题，从哪里开始排查？

传统的 Git commit 记录里，这些信息都不在。有的只是一行 commit message，可能就是 AI 自动生成的，比如："Refactor authentication module"。

**不信任、不理解、不可追溯**——这三个问题，在 AI 代码占比快速上升的 2025 年，变成了工程团队的真实日常。

Dohmke 离开 GitHub 之后，花了几个月时间和开发者聊。他在公开采访里描述看到的场景："我们正在经历一场 Agent 浪潮，AI 正在以任何人类都无法合理理解的速度生成大量代码。"

他把这个问题比喻成制造业的演进：**从手工作坊时代进入工厂时代，你不能只是把机器搬进作坊，然后用以前管工匠的方式去管机器。你得重新设计整个生产管理体系。**

GitHub 是为手工作坊时代设计的。

Entire 想从零开始建工厂时代的管理系统。

---

## 三、博弈

理解 Entire 在做什么，需要先看清楚 AI Agent 开发者工具这个赛道的竞争态势。

这个市场有多大？Markets & Markets 的预测是：AI Agent 市场将从 2025 年的 78 亿美元增长到 2030 年的 526 亿美元，年均复合增长率 46%。

但"市场大"这个判断对竞争分析的意义不大。更关键的问题是：这个赛道里，**谁在哪个层卡位**？

目前这个赛道大概分三层：

**模型层**是 OpenAI、Anthropic、Google。这些公司提供 AI 能力本身。模型更强的，就有更多定价权。竞争最激烈，护城河也在不断被侵蚀——今天遥遥领先，三个月后可能就被追平了。

**框架层**是 LangChain（GitHub Star 超过 80K）、CrewAI（已经融了 1800 万美元 A 轮，每天执行 10 万次以上的 Agent 任务，60% 的 Fortune 500 在用它）、微软的 Agent Framework。这些工具让开发者能快速搭建多 Agent 协作系统，互相调用、互相监督。框架层的竞争同样激烈，玩家众多，切换成本相对低。

**平台层**是目前最稀缺的位置：谁能成为开发者管理 AI Agent 工作输出的基础设施？

这三层的商业价值不对等。模型层和框架层的竞争，注定是一场技术军备竞赛，快速迭代、快速被超越。而平台层一旦被确立，切换成本极高——你的代码历史、审计记录、工作流配置都在里面，迁移的代价就像从 GitHub 迁走一样痛苦。

Entire 选择的是第三层。

但和框架层公司不同，Entire 的定位不是帮你**搭** Agent，而是帮你**管 Agent 产生的结果**。

这个区别很关键。

LangChain、CrewAI 解决的问题是：怎么让多个 AI Agent 协作起来，流水线式地完成一个复杂任务？

Entire 解决的问题是：这些 AI Agent 完成任务、产出代码之后，工程团队怎么理解它们做了什么、为什么这么做、出了问题怎么追溯？

Dohmke 的表述很直接："我们不做模型训练，不做 Agent 开发，我们和这些做集成。"

这个定位，和当年 GitHub 与各种编程语言的关系很像。你用 Python 还是 Go 还是 Rust 写代码，GitHub 都能托管，都能版本控制。你用 Claude 还是 Gemini 还是 GPT 写代码，Entire 都应该能记录、审计、管理产出。

语言无关。Agent 无关。这是一个**中立的基础设施层**的定位。

第一个产品 Checkpoints，是一个开源命令行工具。它做的事情很具体：每当 AI Agent 提交代码，Checkpoints 自动把这次提交的**完整上下文**一并记录——原始 Prompt 是什么、AI 做了哪些推理决策、调用了哪些外部工具、消耗了多少 Token、中途有没有被推翻重来再来一遍。

所有这些信息，和代码一起存进 Git 仓库，并附上可视化界面。

效果是这样的：三个月后，线上的认证模块出了故障。工程师打开 Checkpoints 的记录，直接能看到：当初让 AI 写这段代码的时候，给出的 Prompt 是什么、AI 当时返回了哪几个方案、最终选了哪个、这个选择是因为什么逻辑……

不用去找写这段代码的人问——或者说，根本没有"写这段代码的人"，有的只是提 Prompt 的人。而 Checkpoints 记录了这个 Prompt。

**可追溯，就是可审计。可审计，就是可信任。**

Entire 的完整平台架构分三层：一个兼容 Git 的数据库，用来统一存储 AI 产出的所有代码；一个语义推理层，让多个 AI Agent 能共享上下文、相互理解对方做了什么；以及一个面向 Agent 与人类协作设计的 UI，让工程师能批量审核、批准、或驳回 Agent 的输出。

目前 Checkpoints 支持 Anthropic 的 Claude Code 和 Google 的 Gemini CLI，更多工具的接入还在路上。

## 四、赌注

开源是 Entire 的起点，但不是终点。

背后的商业模型，是 GitHub 走过的那条路：用开源产品建立开发者信任，然后用企业版变现。

Dohmke 在 GitHub 四年，深知这个路径的难点在哪里。

开发者不信任黑箱。如果 Entire 是一个闭源产品，说"我们帮你记录 AI 的所有操作"，没有工程师会放心把自己公司的代码和 Prompt 交给它。开源让他们能看到：Entire 到底在记录什么、数据是怎么存储的、有没有把数据传到外部服务器。

一旦这道信任门槛跨过去，企业版的价值才能显现。

企业版要回答的问题，已经不只是工程效率层面的，而是治理层面的：**我们公司所有 AI 产生的代码，有没有合规风险？有没有潜在的安全漏洞被遗漏？有没有不同的 Agent 在重复解决同一个问题、造成 Token 浪费？**

这个问题，在 AI 代码占比从 2024 年的 20-30% 涨到 2026 年的 50% 以上的过程中，已经变成了每个技术负责人的真实痛点。

不只是工程效率问题。这是一个**治理问题**，一个**合规问题**。

就像**财务部门需要能审计账本**，工程部门也需要能审计 AI 代码的工具。而且随着监管机构开始关注 AI 生成内容的责任归属问题，这个需求只会越来越强。

Dohmke 说了一句话，很能体现他对这个时代节点的判断："2026 年，任何一个技术负责人在考虑团队成本的时候，考虑的已经不只是工程师的薪资、差旅和福利，还有 Token——AI 运行的消耗。这是一个全新的成本维度，过去完全不存在。"

**Token 成为成本**，就意味着需要管理 Token。管理 Token，就需要知道每一次 Agent 运行消耗了多少、产出了什么、值不值得。

这是 Entire 的更长期的价值所在。

但 Entire 面对的最大挑战，可能不是技术，而是时间窗口。

GitHub 没有闲着。Copilot 在 2026 年推出了 Agent Mode，直接内嵌 AI Agent 管理功能。微软把 AutoGen 和 Semantic Kernel 合并成统一的企业 Agent 框架，计划在 2026 年 Q1 正式 GA，带企业级 SLA 和多语言支持。

这些大公司动作的逻辑很清楚：**Agent 管理能力**，是开发者平台争夺下一个十年控制权的关键位置。谁先把它做进工具链里，谁就能**锁住开发者**。

Dohmke 对这个风险当然不陌生——他曾经在 GitHub 内部推动过很多 Copilot 相关的配套工具，但大公司的节奏就是慢，流程多，优先级排队。

他出来创业，或许正是因为这种判断：**这个问题需要一个专注的小团队在两年内拿下，而不是一个大公司的某个产品线在五年内慢慢做。**

Felicis、Madrona、M12（微软的风投部门）……这几家愿意在种子轮押注 6000 万美元，说明它们认同一件事：AI Agent 的时代，管理层工具的需求是真实的，现在的市场里几乎没有成熟玩家，而 Dohmke 是这个问题最合适的解题人之一。

有一个细节很有意思：M12 的参与——这是微软的战略投资部门，也是 GitHub 的母公司系。微软的钱投进 Entire，可以理解成一种**战略对冲**：如果 Entire 的路线对了，微软可以在早期建立关系；如果 GitHub 的 Copilot Agent Mode 赢了，M12 的这笔钱也不过是种子轮的小额布局。

6000 万美元的种子轮，在开发者工具历史上没有先例。

这是一个赌注，赌的是 AI 写代码这件事不是临时现象，而是**永久性的行业基础设施转变**——而基础设施，从来都是最早进入的那个人的游戏。

## 五、三次跃迁

从代码托管（GitHub），到 AI 辅助编程（Copilot），再到 AI Agent 编排平台（Entire）——

这条产品进化线，本质上是**开发者生产力中枢的三次跃迁**。

2008 年，GitHub 卡住了"代码在哪里"这个位置。一个工具从工程师的本地目录变成全球可访问的协作平台。

2021 年，Copilot 卡住了"AI 在哪里帮你写代码"这个位置。AI 以最小摩擦的方式进入了工程师的日常工作流。

2026 年，Entire 想卡住的是"AI 写完代码之后的管理、审计和追溯"这个位置。

每一次，都有人在范式刚开始转变的时候，卡住了那个事后回看"显然应该占住"的位置。

这类机会有一个共同特征：当时做的人，往往被认为太早了，或者在解决一个"还不存在"的问题。但等到问题已经存在，位置也早就被别人占了。

2007 年，如果你说"要建一个网页给工程师托管代码"，很多人会说：本地磁盘不就行了，为什么要放到网上？

2020 年，如果你说"要让 AI 帮工程师补全代码"，很多人会说：代码的逻辑是人的思维，AI 根本做不到。

2026 年，如果你说"要建一套工具管理 AI 写的代码"，有人会说：AI 还没强到那个程度，这个问题还不急。

但 Dohmke 已经看到了：2025 年，在 GitHub 旗下的数百万开发者用户中，AI 生成代码的占比已经超过了 30%，而这个数字正在每季度以两位数的速度增长。

可追溯性的问题，已经是现在时，不是未来时。

**成为开发者工具的基础设施层，在每次范式转移时都是最稳的位置——不是因为你比别人强，而是因为你比别人早，早到成为了标准。**

---

但有一个问题，或许是整件事里最值得停下来想的。

如果未来 80% 的代码都由 AI 写成，那么"开发者"这个身份本身，会不会发生一次更大的变化——从"写代码的人"变成"管 AI 写代码的人"？

你能理解这个区别意味着什么吗？

写代码，需要的是编程能力、算法思维、架构设计能力。

管 AI 写代码，需要的可能是完全不同的技能：怎么给 AI 写出好的 Prompt、怎么验证 AI 的输出、怎么设计 AI Agent 之间的协作流程、怎么在合规和效率之间做权衡。

或者，更进一步：如果 AI Agent 已经强大到完全不需要人类逐行审核，Entire 现在做的这套追溯工具，会不会只是一个过渡阶段的产物？

这是我没有答案的问题。

Dohmke 押注的是：未来的开发者不消失，但工作性质从"生产代码"变成"管理 Agent 生产代码的过程"。这中间的过渡期，短则五年，长则十年，而 Entire 要在这个过渡期里建立不可替代的基础设施地位。

这个赌注对不对，可能要再等两三年才有线索。

但 6000 万美元的种子轮已经说明了一件事：

**目前能把这个问题说清楚的人，和愿意为这套解法付钱的机构，都已经站好了位置。**

至于下一个占住基础设施位置的人是 Entire，还是又一个我们现在还没见过的名字——这是这个时代最有意思的问题之一。
