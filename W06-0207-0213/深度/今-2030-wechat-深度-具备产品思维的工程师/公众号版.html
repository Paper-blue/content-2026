Agent 时代，一条报错能毁掉整个任务

文 / Zayen知蓝

大部分工程师最怕收到的消息，不是来自老板，是来自自己写的系统。

凌晨两点，告警响了。你打开日志，看到一行报错：Cannot deliver a Channelz message to channel @barnyard-friends: channel does not exist。作为写了这段代码的人，你立刻知道问题在哪——频道名写错了，用了 @ 前缀而不是 #。改一下，十分钟搞定。

但如果看到这条消息的不是你呢？

一个刚入职的运维同事，一个不了解 Channelz 内部实现的产品经理，或者一个正在调用你 API 的外部开发者——对他们来说，"channel does not exist"基本等于什么都没说。频道明明存在，为什么说不存在？是被删了？是权限问题？还是系统出了 bug？

Drew Hoskins 在技术行业干了二十多年——Microsoft、Facebook、Oculus、Stripe、Temporal——他花了 18 个月写了一本书，叫「The Product-Minded Engineer」。书里有一个判断挺反直觉：诊断信息可能是你产品最重要的界面。

不是首页，不是核心功能，是报错。

一、低估

这个判断的依据不复杂。

想一下你每天写代码的时间分配。写新功能、写业务逻辑的时间有多少？处理报错、lint 规则、类型检查、调试信息的时间又有多少？Hoskins 的说法是，后者至少占一半。

用户那边也差不多。填电子表单的体验，基本上就是不断被告知哪里填错了、哪里格式不对。使用一个复杂应用的时间里，有相当一部分花在跟错误提示和警告打交道上。

但大多数团队花在错误消息上的设计精力，几乎为零。功能有 PRD，UI 有设计稿，报错信息呢？工程师写代码的时候随手填的一个字符串。

二、分类

错误不是一类东西。Hoskins 把它拆成了五种：

系统错误——服务挂了、网络断了、磁盘满了。用户没法修复，只能等。消息的目标：告诉用户发生了什么，以及大概什么时候能恢复。

用户无效参数——邮箱格式不对、密码太短、文件太大。用户可以修复。消息需要精确指出哪里错了，怎么改。

前置条件未满足——没有付费、没有绑定信用卡、没有开通某个权限。用户需要先完成另一个操作。消息要给出那个操作的入口。

开发者无效参数——API 调用方式不对。面向的不是终端用户，是集成你产品的开发者。

断言失败——不该发生的事情发生了。面向的是你自己的团队。

五种错误，面向不同的人，需要完全不同的措辞和处理策略。但在大部分代码库里，它们混在一起，统一抛一个 Error: something went wrong。

三、边界

哪里抛错误，比怎么写错误消息更重要。

Hoskins 举了一个他做的告警系统 ChickenLittle 的例子。系统要给 on-call 的人发告警，流程很简单：查到 on-call 用户 → 发消息。

最初的实现是：直接把用户 ID 传给下游的消息 API。如果 on-call 排班表里配了一个不存在的用户，下游 API 会返回一个莫名其妙的错误——user not found。收到这条消息的人根本不知道问题出在排班配置上。

改进后的做法：在发消息之前先验证 on-call 用户是否存在。如果不存在，ChickenLittle 自己生成一条消息："排班表里的用户找不到了，点这里修复你的 rotation。"

区别在于错误在哪个层级被捕获。在接口边界——API 或 UI 这一层——你同时拥有两个上下文："发生了什么"和"用户想做什么"。越往底层走，后一个上下文越模糊。

一条从数据库驱动层冒上来的 user not found，到了用户面前，已经完全没有业务含义了。

四、可操作

回到开头那个 Channelz 的例子。

同一个错误，三种消息

差：Cannot deliver a Channelz message to channel @barnyard-friends: channel does not exist

好一点：Channel @barnyard-friends not found. Did you mean #barnyard-friends?

最好：Channel @barnyard-friends uses @, but we found #barnyard-friends. Is that what you meant?

三个版本的信息量完全不同。第一个只说了"出错了"。第二个说了"可能是这个原因"。第三个说了"原因是这个，你要不要试试这个？"

Google 搜索的"Did you mean..."是这个思路的极致——不只告诉你拼错了，直接给你一个可能正确的结果。

好的错误消息回答两个问题：发生了什么？用户能做什么？用产品语言，不是实现细节。

还有一个容易忽略的细节。有些操作风险很高但不一定是错误。比如有人配了一个重试策略：600 秒内重试 601 次，超过了系统的 50 次限制。这不是"错误"，是一个需要警告的高风险配置。弹出警告，同时提供 --force 让用户覆盖——尊重用户的判断，但确保他知道自己在做什么。

五、前移

更高级的做法不是写更好的错误消息，是让错误根本走不到那一步。

Hoskins 用了一个词：Shift Left。把校验尽可能往前移。

信用卡号和 ISBN 编码里都有一个校验位。在你提交表单之前，系统用一个简单的数学运算就能判断号码格式是否合法。这个检查几乎不花计算资源，但能拦掉大量无效输入，避免它们走到后端支付接口才被打回。

Stripe 的测试模式是另一个例子。提供一组特殊的测试卡号，每个触发不同的错误场景——余额不足、卡过期、CVV 错误。商户在接入真实交易之前，就能完整测试自己的错误处理逻辑。

把便宜的检查放在前面频繁执行，贵的检查放在后面按需触发。这在数据管道设计里是基本原则，用在产品设计上同样成立。

六、Agent

这些原则在 2026 年多了一层新的压力。

AI Agent 正在成为产品的重度用户。Agent 调用 API、解析响应、根据结果决定下一步动作。遇到错误时，它纠错的依据就是错误消息本身。

对 Agent 来说

Error 500: Internal Server Error → 死路，无法判断下一步

Rate limit exceeded. Retry after 30 seconds → 明确的行动指令

差的错误消息在人的场景下只是体验不好。在 Agent 的场景下，直接导致任务失败和成本浪费。Hoskins 的团队在 Temporal 已经开始用 AI 工具聚合来自 Slack、GitHub Issues、社区论坛的用户反馈，从中定位最高频的错误场景。

错误消息的质量，正在从"体验问题"变成"系统可靠性问题"。

产品思维不是一种天赋。Hoskins 给出的练习方法很朴素：多问"为什么"，不期望总能得到清晰的答案；在系统视角和用户视角之间反复切换；参与客户支持，因为那里才能看到用户真正卡住的地方。

John Carmack 在 Oculus 的时候，技术能力毋庸置疑，但他花大量时间做的事不是写渲染引擎——是亲自推动 Netflix 和 Mojang 把应用带到 Oculus 平台上。没有内容的 VR 头显只是一个昂贵的摆设。

能把代码写好的工程师很多。能退后一步想"用户看到这条消息的时候在想什么"的工程师，没那么多。

区别可能就从一条报错信息开始。

本文受 Gergely Orosz 与 Drew Hoskins 的「The Product-Minded Engineer」启发。
