OpenClaw 没你想的那么神

文 / Zayen知蓝

一月底，OpenClaw 的 GitHub 星标一周之内冲到了十几万。

项目经历挺戏剧性——奥地利工程师 Peter Steinberger 最初花了一个小时，用一段脚本把 WhatsApp 接到 Claude API 上，取名 Clawdbot。Anthropic 发了商标投诉，改叫 Moltbot。三天后 Steinberger 觉得名字不顺嘴，又改成了 OpenClaw。

真正把它推上风口的是 Moltbook——一个只允许 AI 代理发帖的社交网络。数千个跑着 OpenClaw 的 agent 自主注册、互相对话，人类只能围观。一周 200 万访客，科技媒体全在写它。

我就是在这波热度里注意到的。不是工作需要，纯粹好奇。

一、选机器

OpenClaw 的定位是本地运行的 AI 代理。不是网页聊天界面，而是跑在你自己设备上的 daemon 进程，通过消息平台接收指令，在本地执行——操作文件、跑 shell 命令、浏览网页、管理日历。

要让它有用，得 7x24 跑着。笔记本显然不行。

一开始我想省事，试了轻量应用服务器。看着便宜够用，但 OpenClaw 很多配置需要在终端里交互式操作，Gateway 启动、消息渠道对接、权限白名单设置，每一步都要在终端里来回调试。轻量服务器的 Web Terminal 体验太差，命令稍微复杂一点就卡住。

折腾了一圈，最后选了新加坡的腾讯云 VPS。2 核 8G，SSH 直连，环境干净可控。

这个选择过程本身就说明了一些事情：OpenClaw 面向的是能熟练操作服务器的开发者。

二、跑通

安装不复杂：

npm install -g openclaw

openclaw onboard

引导向导会依次问你：用哪个 AI 模型、接哪个消息渠道、开放哪些权限。我选了 Claude 作后端，消息渠道接飞书。

飞书对接比我预想中顺畅——创建飞书机器人，配好 webhook，OpenClaw 填上 token，消息就通了。在飞书里给 VPS 上的 AI 代理发指令，它执行完把结果发回来。

第一次在手机上发了一句"帮我看看服务器磁盘使用情况"，几秒后收到了格式整齐的 df -h 输出。

平时要 SSH 登上去才能看的东西，在聊天界面里问一句就行。

三、四个场景

跑通之后，我陆续把几个实际需求搬了上去。

IBKR 盯盘。Interactive Brokers 的行情监控，之前是自己写脚本 + cron 定时跑，报警发邮箱。换成 OpenClaw 之后，飞书里直接通知，还能追问："这个波动什么原因？"——它会去查相关新闻。比纯脚本多了一层上下文能力。

每日新闻创作。定时抓取 AI 行业新闻，整理摘要，生成初稿。和已有的内容工作流可以衔接——OpenClaw 负责前期信息收集和粗加工，后续编辑还是在本地完成。

远程部署。一些实验性项目，之前要 SSH 上去手动跑命令。现在飞书里说"把 xx 项目重新部署一下"，它会走 git pull、build、restart。省了开终端的步骤。

定时执行 Skill。投入时间最多的场景。也是踩坑最深的。

四、Cron 的坑

OpenClaw 有一套 AgentSkills 技能系统，每个 skill 是一个带 YAML 配置的 Markdown 文件，定义了 AI 执行某类任务的流程和约束。社区维护的 ClawHub 上有上百个现成技能，也可以自己写。

我设想的用法是：写好 skill，配上 cron 定时触发，让 OpenClaw 像一个 7x24 的执行员，定时完成各种任务。

调试的时候撞上了一个问题：cron 触发的任务不能开启 sub-agent。

如果 skill 内部需要调用子代理并行处理子任务——比如同时抓取多个新闻源、同时分析多个标的——cron 模式下跑不通。只能串行执行主流程，sub-agent 的调度链路在 cron 上下文中是断的。

调了很久才确认这不是配置问题，是架构限制。

最终我把 skill 逻辑拆开，需要并行的部分改成串行步骤，绕过 sub-agent。能跑了，但效率打了折扣。等于手动做了一次降级。

OpenClaw 的 cron 调度和交互式执行，底层走的不是同一套能力。交互模式下可以开 sub-agent、做复杂编排；cron 模式下更像一个受限的脚本执行器。

文档里没写这一点。

五、回归

刚开始用的时候，预期设高了。

17 万 stars、铺天盖地的报道、Steinberger 在 YC 采访里说"80% 的 App 将在未来消失"。很容易觉得这是一个能替你做一切的 AI 管家。

我也是这么想的。一上来就想把手头能自动化的事情全交给它。

用了一段时间，认识往回调了：它本质上还是一个远程执行环境里的 Claude Code 级别能力。核心智能来自后面接的大模型，OpenClaw 提供的是执行层基础设施——消息通道、文件系统访问、shell 权限、定时调度、记忆存储。

它能做好的事情有共同特征：任务边界清晰、步骤可预定义、容错要求不高。盯盘通知、定时抓取、模板化的内容生成、简单的运维操作。

做不好的也有共同特征：需要复杂判断、上下文极长、结果不可预期。

和直接用 Claude Code 一样，它会犯错、会理解偏、会在复杂场景下走偏。

区别在于：Claude Code 出问题你就在终端里，能立刻介入。OpenClaw 出问题时你可能在外面，只能在飞书里一条条修正。

这种感觉，用过才知道。

六、安全

安全绕不开。Cisco 的博客直接管它叫"安全噩梦"，Bitdefender 发现 ClawHub 上近 20% 的技能包含恶意代码，韩国几家大型科技公司已经在内部禁用。有安全研究员在不到两小时内成功劫持了一个 OpenClaw 实例。

指向很一致：一个需要高系统权限才能发挥全部能力的工具，安全架构在设计之初被低估了。

我自己没遇到安全事故。但场景也比较克制——VPS 本身是隔离的，不是主力工作机；飞书有身份认证；命令白名单配了，只开放必要权限。

在企业环境或存放重要数据的机器上跑，确实要谨慎。几条我自己在用的原则：

• 不要在主力工作机上运行，用独立 VPS 或 Docker 容器

• 命令白名单从最小权限开始，按需开放

• ClawHub 上的第三方技能先审查代码再装

• 定期跑 openclaw security audit --deep

七、适用

OpenClaw 不是给所有人的。

它适合对 Agentic AI 有好奇心、能操作 Linux 服务器、有明确的自动化场景、愿意花时间调试的人。

如果需求主要是写代码，Claude Code 更直接，安全性也更可控。如果要可视化的工作流编排，n8n 更成熟。OpenClaw 的位置在于把 AI 代理能力和即时通讯打通了——在手机上、在任何有消息 app 的地方，指挥一台远程机器做事。

想上手的话：先在本地用 TUI 跑通基本功能，确认模型和消息渠道没问题。然后挑一个简单的任务——比如定时查看服务器状态并通知——做成 skill 跑起来。等跑稳了，再逐步加场景。

不要一上来就想让它自动化一切。

选对场景比什么都重要。
