90% 代码由 AI 写，为什么他选 Claude 而非 GPT-5.2？

文 / Zayen知蓝

Tenex 的工程师 CJ Hess 在最近的一次访谈中提到，他已经三个月没写过一行 JavaScript 或 HTML 了。AI 处理了超过 90% 的前端编码工作。但有意思的是他的选择：在拥有 GPT-5.2 的情况下，他依然选择 Claude 作为主力模型。理由是"Claude 更易引导"。

这个数据本身不算稀奇——市面上关于"AI 提效"的案例已经很多。但有意思的是他的选择：在拥有 GPT-5.2 的情况下，他依然选择 Claude 作为主力模型。理由是"Claude 更易引导"。

如果 GPT-5.2 在原始智能上更强，为什么"易引导"反而成了决定性优势？

核心数据

意图理解能力的价值

CJ 用的词是"意图理解"。他认为 Claude 在理解细微需求方面表现更好，尤其是在需要深度理解的复杂编码任务中。

这和我们通常理解的"智能"不太一样。GPT-5.2 可能在推理能力、知识广度上领先，但如果模型无法准确捕捉开发者的真实意图，那么再强的生成能力也会偏离目标。

换句话说，AI 辅助编程的瓶颈不在"能不能写出代码"，而在"能不能理解我想要什么"。

这个判断直接影响了 CJ 后续的工具设计思路。

技能模块：从通用 AI 到领域专家

CJ 为自己开发的 Flowy 工具构建了专门的"技能"模块。这些技能教会 Claude 如何为特定工具生成格式化输出——比如流程图的 JSON 结构、UI 原型的参数配置。

技能模块是"不断改进的生态系统"。每次 Flowy 工具演进，对应的技能也会更新。Claude 在这个过程中逐渐从通用模型变成了"Flowy 的领域专家"。

与其期待 AI 理解所有场景，不如给它建立一套可训练的规范。

技能模块本质上是中间层——它把开发者的自然语言需求翻译成 Claude 能稳定输出的结构化数据，再把这些数据喂给 Flowy 引擎。这个中间层的存在，让整个工作流从"随机生成"变成了"可预测的自动化"。

技能模块作为中间层的架构示意

视觉化的认知杠杆

Flowy 工具做的事情很简单：把 Claude 生成的 ASCII 图表转换成交互式可视化。

信息量没有变化——ASCII 图和交互式原型包含的数据完全一样。但 CJ 观察到，视觉形式能大幅降低认知负荷。

人类大脑处理视觉信息的速度远快于文本。当你看到一个流程图，可以瞬间理解分支逻辑；但如果是文字描述，需要在脑海中重建结构。

不要强制人类适应 AI 的输出格式，而是让 AI 输出适应人类的认知偏好。

双模型审查体系

CJ 的工作流中还有另一个设计：Claude 负责快速生成功能代码，GPT-5.2 Codex 负责审查。

Claude 的意图理解能力让它更擅长原型化，但代码质量可能不够稳定。GPT-5.2 Codex 在识别代码异味、逻辑不一致和重构机会上表现更好。两个模型的对话产生的代码质量，超过了任何单一模型。

AI 工程不是选择"最好的模型"，而是组合不同模型的优势。

软件工程中的"代码审查"机制，过去是人审查人，现在是模型审查模型。

双模型协作的代码审查流程

从"写代码"到"管理 AI 团队"

CJ 在访谈中用了一个表述："管理多支 AI 队伍"。这是开发范式的根本变化。

传统开发是"我写代码 → 代码执行"；AI 辅助开发是"我描述需求 → AI 写代码 → 我审查"；而 CJ 的工作流已经演进到"我调度多个 AI → 它们协作完成任务 → 系统自动审查"。

这个转变意味着开发者的角色从"执行者"变成了"调度者"。你需要知道哪个模型擅长什么、如何设计它们之间的协作逻辑、怎样建立质量把关机制。

生成层：Claude 快速原型化，处理从需求到代码的转换。

审查层：GPT-5.2 Codex 进行质量把关，捕捉潜在问题。

可视化层：将抽象的代码转化为直观的交互界面，降低认知负荷。

这三层不是线性流程。每一层的输出都可能反馈到上一层，形成持续优化的闭环。

真正可迁移的不是具体工具配置，而是工程化思维：把 AI 当作可训练、可组合、可审查的组件，而非黑盒。

权限与信任的平衡

CJ 还提到一个有意思的细节：他创建了一个名为"Kevin"的 Claude 别名，赋予它绕过某些限制的权限。

他的逻辑是，在有 Git 版本控制的保障下，这类"危险操作"的风险是可控的。即使 AI 做出了错误决策，也可以快速回滚。

对 AI 设置过多限制会牺牲效率；完全放开又可能引入不可控风险。CJ 的方案是：在有安全网的前提下，尽可能减少摩擦。

一个尚未完全解决的问题

回到开篇的那个矛盾：为什么"易引导"比"更聪明"重要？

CJ 的实践给出了一个方向性的答案：AI 辅助编程的核心不在模型能力的绝对值，而在人机协作系统的整体效率。

一个"更聪明"但难以引导的模型，可能需要开发者花大量时间调整提示词、验证输出、修正偏差。而一个"易引导"的模型，虽然单次生成质量可能不是最高，但配合技能模块、可视化工具、审查机制，整个系统的产出效率反而更高。

AI 工程的未来可能不在模型参数竞赛，而在如何让机器理解人的意图。

但这个问题本身还在演进中。意图理解能力如何量化？不同模型的"易引导性"如何评估？技能模块的最佳粒度是什么？

CJ 的案例提供了一个实践样本，但远不是终点。
