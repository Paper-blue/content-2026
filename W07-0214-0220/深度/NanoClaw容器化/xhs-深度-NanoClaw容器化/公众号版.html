90% 自动化背后：Claude Code 从代码助手到工程系统的架构实践

文 / Zayen知蓝

很多人把 Claude Code 当成"更聪明的 Copilot"。打开编辑器，问它写个函数，生成代码，复制粘贴，继续下一个。这样用当然没问题，但你可能错过了更关键的东西。

CJ Hess 用 Claude Code 实现了前端开发 90% 自动化——三个月没写一行 JavaScript。他把 Claude Code 当成一个可以演化的工程系统来构建。

这里面有三个支柱：Skills 模块化架构、双模型协作工作流、规范驱动开发。听起来很技术，但拆开看，你会发现这些都是可以复用的工程方法。

一、为什么简单套壳走不通

最直观的想法是：拿 Claude API，包一层界面，加点快捷键，就是自己的 AI 编程工具了。

但用不了多久就会发现问题。

第一个问题是输出格式不稳定。你让它生成 JSON，它可能给你 Markdown 代码块包裹的 JSON，可能多一段解释，可能少一个逗号。下游工具要解析这些输出，就得写一堆容错逻辑。

第二个问题是上下文爆炸。最开始你只是让 AI 写一个组件，后来你希望它能记住整个项目的架构、代码风格、依赖关系。这时候上下文已经塞不下了，AI 开始"遗忘"之前的规则，输出质量下降。

第三个问题是理解偏差。你说"重构这个模块"，AI 可能理解成"重写"，也可能理解成"优化性能"，还可能理解成"改个变量名"。如果没有明确的规范，每次都是在赌 AI 能否理解你的真实意图。

这些问题的共同点是：你把 AI 当成一个黑盒在用，输入不明确，输出不可控，中间过程不透明。

CJ Hess 的做法不一样。他做了一个叫 Flowy 的工具——把 Claude 生成的 ASCII 流程图转换成可交互的可视化图表。这个工具本身不复杂，但它揭示了一个思路：

让 AI 的输出适配人的认知方式。

二、Skills：可演化的模块化能力体系

Skills 是 Claude Code 里的一个概念——你可以把它理解为"给 AI 定义的专项能力"。

每个 Skill 是一组明确的指令，告诉 Claude 在特定场景下应该怎么做、输出什么格式、遵循什么规则。比如：

- 一个 Skill 专门生成流程图 JSON

- 另一个 Skill 专门生成 UI 原型数据

- 还有 Skill 负责代码审查清单

Hess 的做法是：让 Skills 和工具一起演化。

一开始他只有一个简单的 Skill，能生成基础的流程图 JSON。后来他发现节点之间的连线逻辑经常出错，就在 Skill 里加了一条规则："每条边必须明确 source 和 target，且必须在节点列表中存在"。

再后来，他希望流程图能支持条件分支的样式区分，于是在 Skill 里增加了 edgeType 字段的定义和取值范围。

每次调整 Skill，相当于给 Claude 更新了"工作手册"。这个手册越详细，Claude 的输出就越稳定。

这种架构有两个好处：

能力复用

你写好一个 Skill 之后，它就成了你的"AI 工具箱"里的一件工具。下次遇到类似需求，直接调用这个 Skill，不用重新写提示词。

能力叠加

你可以组合多个 Skills——先用生成代码的 Skill 写一个函数，再用代码审查的 Skill 检查它，最后用文档生成的 Skill 输出注释。这样 AI 的能力就不是单点的，而是可以形成工作流。

三、双模型协作：生成与审查的分离

Hess 用的方法是：Claude 负责生成，GPT-5.2 Codex 负责审查。

这个设计很反直觉。一般人会觉得，既然 Claude 能写代码，为什么不让它自己检查自己？或者干脆用最强的模型一步到位？

他的理由是：模型的"能力倾向"不一样。

Claude 更擅长理解意图、快速构建功能。你告诉它"做一个用户登录模块"，它能很快给出可用的代码框架。但它不太擅长"吹毛求疵"——发现代码里的隐藏问题、设计缺陷、性能瓶颈。

GPT Codex 恰好相反。它不如 Claude 那么"灵活"，但它对代码质量的敏感度更高。给它一段代码，它能指出哪里有重复逻辑、哪里可能引发异常、哪里应该提取成函数。

让每个模型做它最擅长的事。你不会让一个擅长头脑风暴的人去做细节检查，也不会让一个擅长 Code Review 的人去快速原型开发。AI 也一样。

四、规范驱动：让 AI 看懂你的项目结构

2026 年开发者圈子里有个新词：Spec-Driven Development（规范驱动开发）。

核心思路是：把项目规范当成唯一的事实来源。每次 AI 工作时，都从规范出发，评估当前代码状态，然后决定下一步操作。

为什么要这样做？

因为 AI 的"记忆"不可靠。它没有人的那种长期记忆能力，你告诉它的规则，可能在几轮对话后就被冲掉了。如果每次都重新描述规则，既浪费 token，又容易遗漏。

更好的办法是：把规则写进项目里。

.ai-spec 文件夹结构

项目架构说明（目录结构、模块依赖）

代码风格规范（命名约定、注释格式）

常用 Patterns（错误处理、状态管理）

依赖版本锁定

Claude Code 在工作时会自动读取这些文件。它不需要你每次都说"记得用 TypeScript"、"记得加类型注解"、"记得用 async/await"。这些规则已经在 spec 里了，AI 直接执行。

这样做有个隐含的好处：项目结构本身就是最好的 Prompt。

如果你的项目结构清晰、文件命名一致、模块边界明确，AI 就能快速推断出你的意图。反之，如果项目结构混乱、命名随意、职责不清，AI 也会跟着混乱。

五、风险与边界：权限管理与防护机制

自动化程度越高，风险就越大。

Hess 的做法是给 AI 开了很高的权限——它可以直接修改代码、安装依赖、执行脚本。这在很多团队看来是不可接受的。

但他用的是一个"迂回"策略：给 AI 创建一个专用身份。

他在 Git 配置里创建了一个名叫"Kevin"的提交者，所有 AI 生成的代码都以 Kevin 的名义提交。这个身份有绕过 pre-commit hook 的权限，可以快速推进开发流程。

但"Kevin"提交的代码不是不检查——而是延迟检查。开发阶段 AI 快速迭代，到了合并到主分支时，再统一跑完整的 CI/CD 流程。

你有 Git 作为安全网。AI 写坏了代码？回滚。AI 改错了逻辑？回滚。AI 删掉了关键文件？回滚。

六、真实案例：从 Flowy 到 1250 万行代码

Flowy 是一个相对简单的工具——输入 ASCII 流程图，输出可交互的可视化界面。代码量不大，几百行 JavaScript。

但它验证了一个关键假设：AI 可以成为工具链的一部分。

更极端的案例来自 Rakuten 的工程师。他们用 Claude Code 在 vLLM 代码库（1250 万行）上实现了一个复杂的技术任务：提取激活向量的方法。

Rakuten 案例数据

7 小时 — 完成任务耗时

99.9% — 代码数值精度

1250 万行 — 代码库规模

关键是：它不是一次性写出来的。

Claude Code 的工作方式是：先分析代码库结构，找到相关模块；然后生成初步实现，运行测试；发现问题后自动调试、修改；重复这个循环，直到通过所有测试。

这个过程更像是"推演式编程"——AI 在不断试错、验证、调整中逼近正确答案。

Claude Code 不是一个"开箱即用"的工具，它更像是一套方法论。

你可以用它做简单的代码生成，但真正的价值在于：把它当成一个可演化的工程系统来构建。

这些事情技术上不难，但需要一个转变：从"用 AI 辅助开发"到"和 AI 协作开发"。

你写代码，AI 帮你补全。或者你定义规则，AI 执行实现。

Hess 三个月没写 JavaScript，因为他把时间花在了更高层次的事情上——设计架构、定义规范、优化工作流。

AI 编程工具改变的可能是这个：让你可以少写代码。把时间留给思考，而不是敲代码。
