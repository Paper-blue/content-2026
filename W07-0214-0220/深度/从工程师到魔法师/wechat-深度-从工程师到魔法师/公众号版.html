OpenAI 工程师管理 20 个 AI 并行工作，代码审查提速 5 倍

文 / Zayen知蓝

代码审查的时间从 10-15 分钟压缩到 2-3 分钟，这个数据第一次出现在 OpenAI 内部分享时，很多工程师的第一反应是"质量肯定下降了"。

但数据显示相反：审查覆盖率更高，遗漏的边界条件更少。AI 重构的是审查流程本身，不是表面的注释补全。

OpenAI API 平台工程负责人 Sherwin Wu 透露，95% 的 OpenAI 工程师日常使用 Codex，而其中相当一部分人已经在管理"10 到 20 个并行的 AI agents"。这个表述第一次让我意识到，我们讨论的可能不是"工具升级"，而是控制流的改变。

效率提升

10-15 分钟 → 2-3 分钟 — 代码审查时间压缩 5 倍

95% — OpenAI 工程师使用 Codex 的比例

从单线程到多智能体并发

传统的代码审查是串行流程：提交 PR → 逐行检查 → 反馈 → 修改。人类的注意力是单线程的，你没法同时检查逻辑正确性、边界条件、命名规范和性能问题。

AI 改变的是把这个串行流程拆成了并行任务。

2026 年 2 月发布的 Codex app 引入了一个关键机制：worktrees——在同一个仓库下创建多个独立的工作副本，每个副本可以切换到不同的分支，同时共享同一个 .git 目录。这解决了核心问题：如何让多个 AI agents 同时工作在同一个代码库上，而不会互相干扰。

每个 agent 拿到独立的 worktree，可以自由地修改代码、运行测试。这些 agent 可能在做完全不同的事：检查类型安全、跑性能测试、生成测试用例、验证 API 文档一致性。所有 agent 完成后，系统汇总反馈，生成结构化审查报告。

这种并行机制改变了协作界面：从"提交代码等反馈"变成"启动审查流程，在多个维度上同时获得结果"。价值在于控制流的转变，速度只是副产品。

AI 带来的是"不同的控制流"，不只是"更快的代码补全"

非确定性作为特性

传统并行编程要求确定性——相同输入产生相同输出。但 LLM 是非确定性的：同一个 prompt 可能得到两个不同但都合理的答案。

OpenAI 的工程师们发现，这种非确定性不是 bug，而是 feature。

实际使用中，开发者会让多个 agent 同时实现同一个功能，每个 agent 独立工作，产生不同的实现方案，最后选择最合适的那一个。这解决了一个长期问题：如何在设计空间中快速探索多个可能性。

过去，开发者构思几个方案后选一个实现，这个过程是串行的。现在，你可以让 10 个 agent 同时探索 10 个方向，然后对比它们的权衡：可读性如何、性能表现、长期维护成本、与现有架构的兼容性。

这让 Sherwin Wu 用了一个比喻："Engineers are becoming sorcerers"（工程师正在变成魔法师）。传统工程师是"手艺人"，一行一行编写代码；现在更像是"召唤师"，指挥多个智能体并行工作，从输出中选择最优解。

"模型会吃掉你的脚手架"

Sherwin Wu 提出："Models will eat your scaffolding for breakfast"（模型会把你的脚手架当早餐吃掉）。他说的是整个"中间层抽象"的逻辑，不局限于某个具体框架。

向量数据库就是典型例子。过去 AI 应用都在用 RAG 架构，核心是向量数据库——切块、生成 embedding、存储、检索。这本质上是在弥补早期模型上下文窗口太小的缺陷。现在模型窗口扩展到几百万 tokens，很多场景下可以直接把文档塞进 prompt。向量数据库从"必需品"变成了"可选项"。

LLM 框架也类似。2024 年的最佳实践是用 LangChain 管理 prompt、chain、memory。但现在越来越多团队直接调用模型 API，因为框架本身成了瓶颈：模型迭代速度远快于框架更新，抽象反而限制了灵活性。

这里有一个残酷的规律：12 个月前的最佳实践，现在可能已经是技术债务。你构建的"优雅架构"，可能在下一个模型版本后就失去意义。架构的边界在移动，模型正在吃掉这条线上越来越多的东西。

框架本身成了瓶颈：模型迭代速度远快于框架更新，抽象反而限制了灵活性。

OpenAI 内部的工程化保障

95% 的采用率不是自然发生的，背后有一套工程化保障：

Agents SDK 提供了结构化输出、上下文管理、会话恢复等功能，几行代码就能集成。

自动化代码审查 让 Codex 审查几乎每个 PR，作为"第一道防线"过滤明显问题，让人类专注于高层次设计决策。

标准化配置文件 如 AGENTS.md 和 MCP（Model Context Protocol），让 Codex 更容易适配不同代码库。AGENTS.md 是给 agent 的"说明书"，告诉它项目结构、编码规范。MCP 允许 Codex 调用 CI/CD、issue tracker 等第三方工具。

这些机制的共同点是：降低人类的认知负担。传统 AI 工具往往增加认知负担，而 OpenAI 的策略是让工具"消失"在工作流中，自然地出现在你需要的时候。

12-24 个月的窗口期

Sherwin Wu 认为：未来 12 到 24 个月是一个关键窗口。

这个窗口的特殊之处在于，模型还没强到可以完全自动化开发流程，但已经强到足以改变工作方式。在这个阶段，能够熟练驾驭 AI 工具的工程师，和用传统方式工作的工程师，生产力差距会迅速拉大。

这是"杠杆"逻辑，不是"替代"。一个会用 AI 的工程师可能比不会用的效率高 5 倍、10 倍。这种差距会在组织层面产生连锁反应：能够系统化采用 AI 工具的团队，会在产品迭代速度、代码质量上形成代际优势。

问题是，大多数工程师还在把 AI 当成"辅助工具"：写代码时让它补全，遇到 bug 时让它给建议。但这没触及核心。AI 带来的是"不同的控制流"，不只是"更快的代码补全"。

你需要学会的是"如何把任务拆解成可以并行执行的子任务，然后让多个 agent 协同完成"。这是一种新的思维方式，需要时间形成。

新的架构边界在哪里

在这个转变过程中，哪些东西会留下来？

测试：无论模型多强，你仍需要可靠的测试体系验证代码正确性。当代码有一部分是 AI 生成的，测试的重要性反而更高。

可观测性：当系统中有多个 agent 并行工作，你需要知道它们在做什么、遇到什么问题、决策基于什么上下文。这需要对整个 agent 工作流的追踪和可视化，远超简单的日志。

领域知识：模型可以生成代码，但代码是否真正解决业务问题，仍需人类判断。判断质量取决于你对业务的理解深度。

新的架构边界可能在这里：模型负责执行，人类负责定义"什么是正确的执行"。

这个边界会不断协商和移动。但有一点确定：未来的工程师需要同时具备两种能力，理解系统和理解模型。

前者是传统工程素养，后者是新的技能树：如何设计 prompt、拆解任务、评估非确定性输出、在多个方案中做权衡。这些正在成为所有软件工程师的基础技能。

Sherwin Wu 用"魔法师"这个比喻，可能比他自己意识到的更准确。

魔法师知道如何召唤、指挥、协调不同力量。在软件开发的下一个阶段，工程师的核心能力可能会从"写出优雅的代码"转向"设计出优雅的协作流程"：让多个 agent 在正确的时间、正确的上下文中做正确的事。

这种能力的形成需要在真实项目中反复试错，对模型能力边界有清晰认知，在"控制"和"放手"之间找到平衡。

12-24 个月的窗口期，留给那些愿意主动探索这个新范式的人。而那些等待"标准答案"的人，可能会发现，等到答案出现时，游戏规则已经变了。
